# 11. Risks and Technical Debt

## 11.1 Risks

| ID | Risk | Likelihood | Impact | Mitigation |
|----|------|------------|--------|------------|
| R1 | Sandbox escape or misconfiguration lets a component access the host. | Low | Critical | Keep `allow-same-origin` forbidden (built, DT-11: the sandbox list is asserted at frame creation, tested, and `npm run lint:boundaries` fails on the flag anywhere in the sources); dedicated security tests; consider hosting the sandbox on a separate origin later (ADR-001c); keep browsers up to date. |
| R2 | Resource exhaustion from a hostile or buggy component (CPU loop, memory, audio). | Medium | Medium | Heartbeat watchdog, ability to kill a frame, trust prompt; browsers offer no hard limits, so residual risk is accepted. |
| R3 | Many iframes make editing slow (thumbnails, multiple components per slide). | Medium | Medium | Lazy frame creation, static snapshots for thumbnails, frame pooling, destroy off-screen frames. Measure early with a stress deck. Built (DT-11, DT-12): a frame exists only while its element is drawn, near the shown slide and (editor) in view, and never in a thumbnail (snapshot or placeholder); counted by `FrameRegistry` and tested with 30 slides of two components (at most 6 frames). Not measured in a real browser yet (11.2). |
| R4 | Editor complexity (selection, snapping, rotation, text editing in a scaled DOM) takes longer than expected. | High | Medium | Build vertical slice first (text + shape move/resize), reuse proven libraries for text and geometry where possible, defer tables and advanced alignment. Built (DT-07): selection, move, resize, rotate, snapping, align / distribute and zoom on the canvas, with pure geometry functions tested on their own; the sorter, insert menu, properties panel, notes and shortcut registry followed in DT-08; in-place text editing on the canvas (ProseMirror, ADR-004) followed in DT-10: the editor is drawn in the scaled overlay, so zoom and rotation need no extra coordinate maths, and it was only checked in jsdom (no layout, no real IME or touch input), so caret placement, composition input and the clipboard in real browsers are still to be tried by hand. |
| R5 | IndexedDB data eviction or loss. | Low–Medium | High | Request persistent storage (built), export bookkeeping for reminders (built, reminder UI pending), rolling backup of the pre-migration version (`BackupSink`, written before a migrated deck is returned, oldest copy always kept), failure banner with retry, one-click export of a deck or of all decks, and a download in the failure banner (built, DT-16). |
| R6 | Component API churn breaks existing decks. | Medium | High | Versioned handshake, host supports previous major, API frozen once released, deprecation policy. |
| R7 | Projector/laptop differences (GPU, fonts) change appearance. | Medium | Low | Embed fonts as assets, fixed stage, pre-flight check in presenter. |
| R8 | Later collaboration requirement conflicts with the local-first model. | Medium | Medium | Patch-based commands and stable ids chosen to ease a move to CRDTs (e.g. Yjs). Not committed. |
| R9 | Safari/Firefox differences in sandbox, fullscreen or File System Access API. | Medium | Low–Medium | Feature detection with fallbacks (download/upload); cross-browser e2e. |
| R10 | An agent produces code that is hostile, or a client wires the server to a folder with private files. | Medium | Medium | The server runs component code only for previews, which the server's owner must enable (`DECKTECH_PREVIEW=1`; sandboxed frames, fresh browser context, no network), and never grants trust (the dialog of ADR-008 decides at import); paths are confined to the workspace folder with links followed; limits and `validateDeck` apply to every change (ADR-013). The human review of the code remains the control. |

## 11.2 Technical debt (accepted for the first release)

| Item | Note |
|------|------|
| No hot-patching of code components | Each edit reloads the frame; state may be lost during authoring. Revisit with HMR-style module swapping. |
| Thumbnails of code components are placeholders unless the component provides a snapshot | A rasterization strategy (e.g. offscreen render by the runtime) can be added. |
| Basic tables and no charts as built-in element | Charts can be written as code components. |
| PDF export of code components is a static snapshot | Print-specific handling not designed. |
| Single-user, single-device | Sync and collaboration deferred. |
| Autosave writes the whole deck | Cost follows deck size (a 1000-slide deck is cloned on every write); blobs are separate and unaffected. Revisit with per-slide records or patch journaling. |
| Unreferenced assets are never collected | `delete(deckId)` and removing an element leave blobs behind. A mark-and-sweep over all decks' `assets` is needed before storage pressure matters. |
| Library thumbnails are placeholders | `library` may not import `renderer` (4.4), so the home screen shows the title's initial. Slide thumbnails there need a rule change or a thumbnail provider in `shared`. Also unbuilt: the export reminder UI. |
| Import limits (DT-16) | The file is read into memory, unzipped synchronously on the main thread (up to 256 MiB, so a large deck freezes the page for a moment; a worker would fix that) and copied once more when it is stored. The compression-ratio rule (200, above 256 KiB) can refuse a legitimate but extremely repetitive file, and the writer does not check it. A failed import can leave unreferenced blobs (see "Unreferenced assets"). The content checks look at magic numbers and encodings, not at whether, say, a PNG decodes. A bundle from "Export all" cannot be imported as one file. No thumbnail is written yet. The real file dialogs were not tried in a browser. In the `<input>` fallback a browser that fires no `cancel` event leaves the choice pending and a hidden input in the page. While a save dialog is open the library queue is busy, so other library actions wait. |
| Library list is paged, not windowed | 60 decks at a time plus `content-visibility`, which meets Q11 for placeholder thumbnails. Revisit with real thumbnails. Renaming or deleting a deck that another tab has open surfaces as a `conflict` or as a failed save there. |
| Canvas limits | Group resize and rotation need unrotated members (no shear); the group has no rotate handle; resizing never flips; snapping covers unrotated boxes and move only (no distance guides); the marquee selects by intersection of bounds. Moves send incremental deltas, so very long drags can leave floating-point noise (about 1e-13) in coordinates. Q9 is measured by hand, not in CI (10.3): tests only check that a move re-renders one element and keeps one history entry. The renderer draws code components since DT-11, but the measured deck has none; repeat the profile with them. Hit targets are one div per element, redrawn from the slide on each change. |
| Editor chrome limits (DT-08) | The sorter draws a `li` per slide (only the thumbnails are lazy), which is fine for the 200 slides of Q11 but is not a windowed list. Drag and drop uses HTML5 drag events, which touch browsers do not fire; the Move up / Move down buttons cover them. Gradient and image fills can be shown and kept but not created; there is no table or video editor in the panel. Reading order and z-order are the same array. The insert menu is a filter plus a list of buttons rather than an ARIA combobox. Inserted pictures are never garbage-collected (see the assets row above). Deleting the slide that starts a section drops the heading. |
| Trust flow (DT-17) | A decision is bound to the hash of each component, so a component the user edits (or adds) in an imported deck is undecided again and the dialog asks once more; the live preview of the code editor is gated like any frame. Network origins cannot be granted. Heuristic flags are hints that obfuscated code defeats; the sandbox is the defence. A re-import is compared with the decision for the same file deck id only while that deck still exists; deleting a deck deletes its record, its snapshots and the "known library" marks it gave. Unchanged re-imports ask again. The fail-open case is a build without a `DeckRepository` (tests and tools), which the app always provides. The presenter shows placeholders but cannot ask. Heuristic formatting can be wrong for regular expression literals. The diff table is capped at 4 million cells per section (coarser beyond). |
| Component host limits (DT-11, DT-12) | Frames are destroyed, not paused, when off-screen (state survives through `deck.state`; anything else the component held in memory is lost, and a component that takes long to start shows its placeholder meanwhile). `distance` is an input of `SlideRenderer` that only the presenter sets (DT-14); the editor leaves it at 0. A thumbnail shows a snapshot only if the component supplied one in this session (snapshots are not persisted or exported); otherwise the placeholder. A presenting frame that missed one heartbeat window is destroyed for good, even if it would have recovered. The 30-slide test counts frames; fps and memory with many live components were not measured in a real browser (Q9 needs the profile repeated with code components, see the canvas row). `deck.state` lives in the host's `localStorage` per deck and element: it is not exported with the deck, not undoable, and never removed when an element or deck is deleted (it needs the same garbage collection as assets); where `localStorage` is blocked it lasts for the session. The `network` grant is not decided anywhere: `ComponentPolicy` grants nothing until the trust dialog (ADR-008) exists, and the `storage` permission has no meaning yet. Imported decks are not gated: code runs as soon as it is drawn, which is safe for the host but not for the data a component already has (see 8.2, residual risk); the trust prompt comes with import. The model has no file names, so assets are addressed by id, not by relative URL, and libraries are imported by asset id. A component that logs in a tight loop is cut off by the flood limit. Two live frames of the same element each hold their own copy of `deck.state` and the later save wins (the code editor's preview uses a separate element id, `el_preview`, and starts empty, so it does not touch the element's state). If the chunk with the code view fails to load, code elements stay blank until the slide changes again. Pointer input into a frame in the editor needs interact mode (5.4). |
| Code editor and component library limits (DT-13) | "Add library" from npm depends on esm.sh (a third-party service) being reachable once; its `?bundle` build is checked for imports from the network but not otherwise reviewed, and a library is stored as given (no hash pinning against a known list yet; the `CodeInspector` of ADR-008 is meant to add that). The library entry is a copy: editing it later does not update decks that already inserted it, and a library entry that is still referenced by no deck is never collected. Removing every instance of a component leaves its definition in `Deck.components`, and removing a library from a definition leaves its asset in the deck (the same missing garbage collection as for pictures). The preview shares the editor's page, not a separate origin; it is as sandboxed as any frame. The checklist is a reminder and the hints are patterns, not an accessibility test of the component. The `network` permission can be declared but nothing grants origins yet (above). The console panel filters by component id, so a second live instance of the same definition (on the slide behind the dialog) mixes its output with the preview's. The properties form commits the valid fields while another field is still invalid, so undo granularity depends on which fields were valid at the time. Hints and dependency flags are recomputed on every keystroke of the draft (regular expressions over at most 1 MB per source); large sources would want debouncing. |
| Presentation limits (DT-14) | Keys pressed while the focus is inside a component's frame go to the frame, not to the presentation (a click into a component moves the focus there, and a frame is a separate document the host cannot listen to): the component can use `deck.navigate`, or the presenter clicks outside the frame. Browsers swallow Escape in fullscreen; leaving fullscreen ends the presentation. Fullscreen needs the user gesture of the click or F5 that started it; if the chunk loads slowly past the browser's limit it is refused and the presentation runs in the window. A preloaded slide's components run (and animate) while hidden. The rest of the app stays in the page behind the fixed presentation layer; it is not made `inert`. Transitions are the slide that comes in animating over the one that goes (no direction for going back). The 100 ms of Q10 and the offline e2e of Q6 are checked in jsdom only (10.6). The engine plans with the counts of frames that exist: on a slide reached by a jump (or the first one) the component's steps appear once its frame has started and declared them, and pressing next before that moves on. |
| Presenter view limits (DT-15) | The presentation window owns position and clock; a presenter view is not told that the presentation ended, and two presentation windows of one deck would both answer commands. The previews are static (`thumbnail`), so a code component's own internal step is not drawn in the presenter window. Opening the window can take some browsers out of fullscreen; this is tolerated for 2 s, after which the presentation fills the window rather than ending. |
| Theme and layout editor limits (DT-31) | A theme belongs to its deck: there is no library of named themes or layouts shared between decks, and a colour token cannot be renamed (add a new one and remove the old). Contrast is measured for hex colours only (the check is a warning, not a block). Layout background editing offers none or a solid colour (gradient and image fills are kept, not created). Placeholders cannot be reordered, so which bound element takes which placeholder of a kind follows creation order. The layout editor's pointer drag and corner handle are exercised by hand, not in jsdom (the keyboard and number-field paths are tested). Re-flowing after a layout edit replaces the geometry of bound, unlocked elements, including ones the author moved by hand. Rich text size marks still name type scale keys; plain text uses `sizeToken`, and a text with neither keeps its own number. |
| Visual design migration (DT-44) | Built and used by every screen (8.11). Left: the editor and tools dialogs still have their own frame in `dialog.css` and `tools-dialog.css` instead of `app-dialog`; sizes and spacing are tokens by habit but only colours are enforced by `lint:tokens`; the look was checked through the tokens, AXE and jsdom, not by eye in a browser, and there are no before / after screenshots yet; tooltips do not open on touch; a "comfortable" density is not built. The colour keywords (`white`, `black`) are not checked, and the contrast pairs are a list, so a new token role has to be added to it. |
| No cross-tab live update | A second tab learns of a change only through a `conflict` on save; a `BroadcastChannel` notification can be added. |
| MCP server limits (DT-46) | Previews need the built app, `playwright` and a Chromium on the machine, run one at a time (a new context per picture, about a second each), take a picture of the first moment after `settleMs` (animations are not followed), and only see the first frame of presentation mode (no steps, no component navigation). The preview page is part of the production bundle although only a script uses it. The browser sees what Chromium sees, not Safari or Firefox. Without previews, syntax is checked with acorn but not that the script works, and the warnings are regular-expression hints. Decks live in memory until `export_deck` (a crash loses them); there is no autosave and no file locking, and the 200-step undo keeps whole documents (structurally shared). The component library is a folder of files, separate from the browser's IndexedDB library, and refuses entries with asset files. No tools for tables, video, lines, sections, backgrounds or layout editing; `check_accessibility` sees alt text, empty text and text contrast only (gradient or image backgrounds and colours that are not plain CSS colours are listed as `notChecked`). An open deck holds at most 256 MiB of embedded files, and the bytes of removed images stay until the deck is closed. The server imports app source by relative path. A stdio server has no authentication; whoever can start it has the access of its process. |

## 11.3 Open questions

1. Should the sandbox be served from a separate origin (stronger, needs hosting) as an option for the hosted variant?
2. Is a TypeScript-in-the-browser option (compiling component TS) worth the bundle cost?
3. Do we want a "block" level between built-in elements and full code (low-code widgets such as quiz or timer)? These could ship as built-in code components in the library.
4. Format for presenter audience interaction (polls, Q&A) which would need a server.
