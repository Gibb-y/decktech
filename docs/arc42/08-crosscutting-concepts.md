# 8. Cross-cutting Concepts

## 8.1 Domain model and document lifecycle

The deck document (section 5.2) is the single source of truth. It is immutable from the outside: the store replaces it with a new value on each command, and unchanged slides and elements keep their object identity, so signals and `computed` selectors only recompute what changed.

Document versions are tracked by `schemaVersion`. Every load or import runs the migration chain; unknown *newer* versions are reported as read-only with a reason (no editable deck is produced).

### Migrations

`migrate(raw)` (`src/app/core/migrations/`) is the entry point in front of `validateDeck`. It never throws: anything unexpected (e.g. a stack overflow on absurdly nested input) becomes an `unexpected` error.

- **Chain:** `MIGRATIONS` maps a version to the pure step that upgrades it to the next one. The runner applies the steps in order and stamps `schemaVersion` itself after each, so a step only transforms content. Bumping `SCHEMA_VERSION` requires adding the step from the previous version (a spec checks the registry is contiguous) and a frozen fixture for the new version (`fixtures.ts`). v0 → v1 is synthetic: no released app wrote v0; it exists to exercise the chain.
- **Atomicity:** an older document is deep-cloned once and the steps run on the clone, so a throwing or in-place-mutating step cannot change the caller's data. A step that throws, returns a non-object, or leaves a gap in the chain gives an error result (`migration-failed`, `no-path`), carrying the starting `fromVersion` and the failing `step`; a migrated deck that does not validate gives `invalid-deck` with the validation paths. A document already at the current version is validated as is, without a copy.
- **Newer versions:** the outcome is `{ readOnly: true, reason, fromVersion, supportedVersion }`. It deliberately carries no deck: the strict validator rejects unknown fields, so a newer document rarely validates, and handing out a `Deck` with a future `schemaVersion` would make read-only a convention. The caller keeps the stored original untouched, shows the `reason`, and must not save over it. A read-only viewer would need its own tolerant reader. A missing, fractional, negative or non-numeric `schemaVersion` is an `invalid-version` error.
- **Backup:** `migrateStored(raw, sink)` is for decks loaded from storage. Only when an upgrade actually happened (and succeeded) it awaits `sink.backup({ raw, fromVersion, toVersion })` with a copy of the untouched original (so an asynchronous sink never sees later changes), and only then returns the migrated deck. If the backup fails the result is a `backup-failed` error, so the caller keeps the stored original and never overwrites it with an un-backed-up migration. Failed migrations and read-only decks need no backup, because nothing is overwritten. The sink is implemented by the repositories (8.5): a rolling store that always keeps the oldest copy.

### Validation

`validateDeck(unknown)` is the single entry point for untrusted documents (import, storage). It returns `Result<Deck, ValidationError[]>`; every error carries a path (e.g. `slides[2].elements[0].w`) and all problems are collected rather than stopping at the first. It enforces:

- **Types and enums:** every field has the expected type; element, fill, transition, permission and prop types are closed sets, so unknown element types are rejected. `Slide.section`, when present, is a non-empty string; it was added as an optional field without a `schemaVersion` bump (nothing was released with the previous shape), so an older build that validates strictly rejects a deck that uses it.
- **Unknown fields:** every object only accepts the fields the model defines, so nothing unmodelled can ride along. In particular a `CodeEl` cannot carry its own `html` / `css` / `js`; code lives only in `ComponentDef`.
- **Numbers:** finite only (no `NaN` / `Infinity`), with range limits on geometry, rotation and `step`.
- **Limits** (`ValidationOptions`, overridable per call): string length, array length, slides, elements per slide, components, assets, table cells, and nesting depth of `CodeEl.props`. Defaults live in `DEFAULT_VALIDATION_OPTIONS`.
- **Tables and videos (DT-20):** a table has at least one row and every row has the first row's number of cells (at least one); `columnWidths`, when present, has one positive finite number per column and `cellFills` one colour (literal or theme token) or `null` per cell, in the shape of `rows`. A video's `poster` must resolve in `Deck.assets` like `assetId`. `TableEl.header`, `columnWidths`, `cellFills` and `VideoEl.poster`, `muted`, `label` were added as optional fields without a `schemaVersion` bump, like `Slide.section`, so an older strict build rejects a deck that uses them; tables written before the rectangle rule with ragged rows are rejected now (none could be drawn or created before). The mime type of the asset behind `assetId` or `poster` is not compared with the element type: a picture behind a video shows a video that does not play, which is harmless.
- **Identity:** ids match `^[A-Za-z0-9_-]{1,128}$`; slide, layout and component ids are unique, placeholder ids are unique within their layout, and element ids are unique across the whole deck.
- **Stage:** `Deck.stage` has integer sides and must keep a width of 1920 or a height of 1080.
- **Referential integrity:** `Slide.layoutId`, `CodeEl.componentId`, every asset reference (image, video, fills, `ComponentDef.files` / `libs`) must resolve; an empty reference is dangling.
- **Assets (import hardening, 8.2):** `mime` must be on a configurable allow-list (`allowedMimeTypes`), and `hash` must be a lowercase hex SHA-256 digest.
- **Placeholders and fonts:** `Element.placeholder`, when present, is one of the placeholder kinds; `Theme.fontFaces` entries have a plain family name (`^[A-Za-z0-9][A-Za-z0-9 _-]{0,63}$`) and an `assetId` that resolves in `Deck.assets`. Both were added as optional fields without a `schemaVersion` bump, like `Slide.section`, so an older strict build rejects a deck that uses them.
- **Rich text:** `TextEl.rich`, when present, is checked by `validateRichText` (5.4, "Rich text editing"): a closed grammar of nodes and marks, link addresses limited to `http(s):` and `mailto:`, colour and size marks naming theme tokens that must exist in `Theme.colors` / `Theme.typeScale`, a nesting depth of 8 for lists, at most 20,000 nodes and 200,000 characters, and no field the grammar does not name (so `__proto__` or `onclick` are errors). It is the same check `SetText` applies, and the renderer additionally ignores anything outside the grammar instead of failing.
- **Theme references:** colours are validated literals (hex, `rgb()`, `hsl()` or a keyword, so no arbitrary CSS can be smuggled in) or `{ token }` references that must exist in `Theme.colors`; `TextEl.font` must exist in `Theme.fonts`.
- **Prop specs:** a default must match the declared type, lie within `min` / `max` for numbers (and `min <= max`), and be one of the option values for selects.
- **Hostile keys:** `__proto__`, `constructor` and `prototype` are rejected as keys in props, theme maps and prop specs. `CodeEl.props` must be plain JSON.

`CodeEl.props` are deliberately not checked against the component's `propSchema`: schemas evolve, and a stale prop must not make a deck unloadable; the renderer ignores undeclared props and applies defaults. Only the current `schemaVersion` is accepted (opening newer versions read-only belongs to `migrate`, not to validation); the migration chain runs before validation. Validation checks structure, not code: the content of `ComponentDef.html/css/js` is opaque here and handled by the sandbox (8.2) and trust prompt (6.4).

### Stage and units

- Logical stage: **1920 x 1080** (16:9; other ratios configurable per deck, keeping a 1080 height or 1920 width).
- Elements use stage units. The renderer wraps the stage in an element with `transform: scale(k)` where `k = containerWidth / stageWidth` (5.7).
- Text is sized in stage units too, so it scales proportionally.

## 8.2 Security model for code components

Threat: a `.deck` file contains JavaScript. If it ran in the host origin it could read every deck in IndexedDB, exfiltrate data, or modify the app.

Defence in depth:

| Layer | Measure |
|-------|---------|
| Process/origin isolation | `<iframe sandbox="allow-scripts">` **without** `allow-same-origin`, so the frame has an opaque origin: no access to host DOM, storage, cookies or IndexedDB. |
| Network | Frame document carries a CSP meta tag: `default-src 'none'; script-src 'unsafe-inline' 'unsafe-eval' blob: ...; style-src 'unsafe-inline'; img-src blob: data:; connect-src 'none'`. Network is blocked unless the component declares and the user grants the `network` permission, in which case `connect-src`/`img-src` are widened to the listed origins only. |
| Capability API | The only way out of the frame is a `MessagePort` whose handler validates a closed set of message types. No generic eval, no DOM access. |
| Feature policy | `allow=""` on the frame: no camera, microphone, geolocation, fullscreen, etc. unless a permission is explicitly granted. |
| Navigation | `sandbox` omits `allow-top-navigation`, `allow-popups`, `allow-forms`, `allow-modals`; links are intercepted by the runtime and opened through the host after confirmation. |
| Resource limits | Message size cap, message rate limit, heartbeat watchdog, memory not enforceable by browsers (documented as residual risk). |
| Consent | Foreign decks open with code disabled until the user trusts them (6.4). Trust is bound to the hash of each component's definition, so a changed component prompts again. The gate is `ComponentPolicy.mayRun` in the renderer: no frame is created for a component that may not run, and the answer is "no" until the decision has been read (fail closed). A deck without a trust record counts as made here; the records are written by import before the deck is stored and are copied by "Duplicate". |
| Import hardening | ZIP bomb limits, path normalization, schema validation, allow-list of mime types for assets, content checks and hashes (below). |

Residual risks (CPU/memory exhaustion, side-channel timing, audio nuisance) are listed in section 11.

### As built (DT-16): the `.deck` reader

`readArchive(bytes)` (`library/archive/reader.ts`) never throws and has no side effects; any failure is an `ArchiveError { kind, message }` with a message fit to show, and nothing is returned. The order is:

1. **Limits, before anything is inflated.** fflate's `unzipSync` filter runs per entry with the sizes of the central directory. Defaults (`DEFAULT_ARCHIVE_LIMITS`, overridable per call): file 256 MiB, 5,003 entries (`maxAssets` + 3), 64 MiB per asset, 16 MiB for `deck.json`, 64 KiB for `manifest.json`, 256 MiB in total, and an uncompressed / compressed ratio of at most 200 for entries above 256 KiB (tiny entries compress very well legitimately). Only stored and deflate entries are accepted. A declared size is never trusted: fflate allocates at the declared size and cannot be made to inflate past it, and after unzipping every entry must have exactly the declared length, so a lie about the size ends in `too-large`, a size mismatch or a hash mismatch, never in more memory.
2. **Paths.** Rejected: empty or over 300 characters, a backslash, control characters, a leading `/` or a drive letter, and any segment that is `.`, `..` or empty. Names that differ only in case count as duplicates. Directory entries are ignored. Then an allow-list: only `deck.json`, `manifest.json`, `thumbnail.png` and `assets/<64 hex>.<ext>` exist, so nothing else is ever looked at. An asset file that the deck does not use is also an error.
3. **Manifest and hash.** `manifest.json` must be `{ format: "decktech-deck", formatVersion, appVersion, schemaVersion, contentHash }`; a newer `formatVersion` is `newer-format` ("update DeckTech"). The SHA-256 of the bytes of `deck.json` must equal `contentHash` before the JSON is even parsed. This is an integrity check (damage, a changed deck.json), not authentication: whoever writes the file writes the manifest too. The same hash is what trust is bound to (ADR-008), and because every asset is checked against the id it is listed under, it covers the whole deck.
4. **Deck.** `migrate` then `validateDeck` (8.1), so an older file is upgraded in memory (Q12) and an invalid one is refused with the path of the first problems. A deck from a newer schema is refused as `read-only` (an import has nothing to show it with).
5. **Assets.** For every asset in `Deck.assets`: the mime type is on the allow-list (also enforced by `validateDeck`), the file name has the extension of that type, id = `hash` = `blobKey`, the size equals `AssetRef.size`, the **content** matches the declared type (`sniff.ts`: magic numbers for the binary formats, valid UTF-8 for scripts and styles, valid JSON for JSON, and for SVG a leading `<svg` element without `<script`, `<foreignObject`, `javascript:` or an `on…=` attribute; a benign file that merely contains such text is refused too), and the SHA-256 of the bytes equals the id. `thumbnail.png`, if present, must be a PNG.
6. **Result** `{ deck, assets, thumbnail?, hasCode, hash, migrated }`; `hasCode` is "the deck declares components".

`DeckArchive.importBytes` is the only code that stores anything, and only after step 6: it gives the deck a new id when the library already has that id (an import never replaces a deck), writes the assets through `putAsset` (content-addressed, shared) and saves the deck. If storing fails after some assets were written, those blobs stay; they are unreferenced but harmless until garbage collection exists (11.2). Before the deck is saved, a deck with components gets a pending trust record (written first, deleted again if saving fails), and the decision of what the imported code may do is the trust flow (6.4, DT-17).

### As built (DT-11)

- **Sandbox.** `createSandboxFrame` is the only code that creates a frame; it sets `sandbox="allow-scripts"`, `allow=""` and `referrerpolicy="no-referrer"` and calls `assertSafeSandbox`, which throws for any forbidden flag or any list other than the approved one. Three guards keep it so: the unit tests (the list, the created element, every forbidden flag), `npm run lint:boundaries` (a forbidden flag in any source or template, a frame created elsewhere) and the renderer test that a definition asking for `allow-same-origin` in its HTML still gets a frame with `allow-scripts` only.
- **CSP.** As in the table, plus `font-src blob: data:` and `media-src blob:` (assets reach the frame as blob URLs), `base-uri 'none'` and `form-action 'none'`. `contentSecurityPolicy(origins)` widens `connect-src` and `img-src` with the normalised origins it is given (https, or http on localhost/127.0.0.1; no paths, no credentials; anything else is dropped), never `script-src` or `default-src`. The origins come from `ComponentPolicy` and only count if the component declares `network`; today the policy grants none (the trust dialog lists the request but cannot allow an address).
- **Bridge.** The bridge parses every message into the closed set of 5.3, with unknown and inherited type names (`toString`), extra fields, wrong types, hostile keys, non-JSON values, depth over 32 and size over 64 KiB (2 MiB for a snapshot image, which must be PNG, JPEG or WebP) refused; 200 messages per second, then drops, then the cut-off. Host messages to the frame are fixed shapes built in the host.
- **Handshake and ports.** Only `ready` from the frame's own window with origin `"null"` is looked at, and only the first; the port is transferred to that window only, and the runtime takes a port only from its parent, once.
- **Navigation.** The runtime cancels link clicks and form submits and turns `window.open` into a `link` message; the host refuses anything but `http(s):` and `mailto:` (`isSafeHref`), asks with a confirm dialog and opens with `noopener,noreferrer`. A second `load` of the frame (it navigated itself, for example with a meta refresh) destroys the frame.
- **Residual risk.** A component can still navigate its own frame (`location = ...`, a meta refresh): the request to that address leaves before the host notices the second `load`, so it can carry data the component already has (props, state) to a server; browsers have no CSP directive to forbid it. Nothing of the host or other decks is reachable. A separate sandbox origin (11.3) would not change this; a trust decision (ADR-008) is the control. The frame's CPU and memory use is not limited either.

**Code written by an agent (DT-46, ADR-013).** The MCP server treats component code as untrusted data: it parses it (acorn, as a module) and by default never runs it (previews, when the server's owner enables them with `DECKTECH_PREVIEW=1`, run it in the app's own sandboxed frames in a throwaway headless browser with no network), and it never writes a trust record, so a deck it exports reads back with `hasCode` and DeckTech shows the trust dialog before anything runs. Its file access is limited to the workspace folder (symbolic links followed); the workspace and library locations come from the client's configuration, not from tool input.

## 8.3 Code component API

Authors write ordinary web code. The runtime script injected into every frame exposes a global `deck` object. The protocol version is `apiVersion` (semver major in the handshake); the host supports the current and previous major.

```html
<!-- HTML -->
<div id="app"><button id="inc">+</button> <span id="n"></span></div>
```

```css
/* CSS */
#app { font: 64px var(--deck-font-body); color: var(--deck-color-text); }
```

```js
// JS (ES module)
deck.ready(({ props, theme, mode }) => {
  let n = deck.state.get('n') ?? props.start;
  const render = () => (document.getElementById('n').textContent = n);
  document.getElementById('inc').onclick = () => { n++; deck.state.set('n', n); render(); };
  render();
});
deck.onProps(p => { /* props changed in editor */ });
deck.steps(3);                   // this component has 3 internal steps
deck.onStep(i => { /* show step i */ });
```

| API | Description |
|-----|-------------|
| `deck.ready(cb)` | Called after handshake with `{ props, theme, mode: 'edit' \| 'present' \| 'thumbnail', size }`. |
| `deck.onProps(cb)` | Property values changed from the properties panel. |
| `deck.steps(n)` / `deck.onStep(cb)` | Participate in the presenter's step engine. |
| `deck.state.get/set` | Small persisted key/value state per component instance (JSON, size-capped). |
| `deck.navigate.next() / prev() / goTo(slideId)` | Request navigation. Honoured only in presentation mode. |
| `deck.assets.url(name)` | Resolves a deck asset to a `blob:` URL available inside the frame. |
| `deck.log(...)` | Forwarded to the editor console panel. |
| `deck.fetch(url, init)` | Present only if the `network` permission is granted. Proxied through the host to enforce the origin allow-list. |
| CSS variables | `--deck-color-*`, `--deck-font-*` injected so components follow the deck theme. |

Property schema (drives the generated properties-panel form):

```ts
type PropSpec =
  | { key: string; type: 'string'|'number'|'boolean'|'color'|'asset'; label: string; default: unknown; min?: number; max?: number }
  | { key: string; type: 'select'; label: string; options: { value: string; label: string }[]; default: string };
```

### As built (DT-11)

Bridge and runtime implement the table above as follows (`API_VERSION` is 1; the host speaks the current and the previous major, so today only 1).

- `deck.ready(cb)` gets `{ props, theme, mode, size }`, `theme` being the `--deck-*` variables, `mode` `edit` or `present`; a callback registered after `init` runs in a microtask. The user module only starts after `init`, so `deck.ready` inside it fires at once. `deck.apiVersion`, `deck.mode` and `deck.size` are readable, `deck` itself is read-only.
- `props` contain exactly the declared props, validated against their spec with the defaults filled in (`resolveProps`, `core/model/props.ts`, shared by the host and the properties panel; the rule for a value is `propValueProblem`: a string of at most 10,000 characters, a boolean, a finite number within `min` / `max`, a colour matching the validator's literal pattern, an asset id or empty, one of a select's options); `onProps` gets the whole new object.
- `deck.state.get(key)` is synchronous (the saved state arrives in `init`); `set(key, value)` stores a JSON copy locally and tells the host, `set(key, undefined)` and `remove(key)` remove. Limits: 64 keys of at most 64 characters and 64 KiB in total; a write beyond them is refused with a warning in the console, and the component's own copy then differs from the saved one.
- `deck.assets.url(assetId)` returns a promise of a `blob:` URL created inside the frame from bytes the host transferred. Only asset ids in the definition's `files` and `libs`, and the ids currently chosen in its `asset` props, are served (the model has no file names, so "addressable by relative URL" is not built); anything else rejects.
- Libraries: each id in `libs` becomes an entry of the import map whose specifier is the asset id, for example `import 'a1b2...'`.
- `deck.navigate.*` is honoured only in `present` mode; the request is published through `CodeHostEvents`. `deck.steps(n)` takes 0 to 1000 and is published the same way; `onStep(i)` receives the index a presenter writes to `CodeHostEvents.stepIndexes`.
- `deck.log(...)` and the page's `console.log/info/warn/error` both go to `HostConsole` (at most 10 arguments, strings cut at 2000 characters); uncaught errors and unhandled rejections arrive as errors. A component that logs more than the rate limit allows loses messages and, in a sustained flood, its frame.
- `deck.snapshot(blob)` is published through `CodeHostEvents.snapshots`; nothing draws it yet (thumbnails show a placeholder, 11.2).
- `deck.fetch(url, init)` exists only when the network is granted (5.3, "Network") and returns a normal `Response`; `init` may carry `method`, `headers` and a string `body`.

`mode` lets a component simplify itself for thumbnails (e.g. render a static frame, skip animation). Thumbnails are produced by rendering the component in `thumbnail` mode and rasterizing the host-side snapshot supplied by the component (`deck.snapshot(blob)`); components that do not provide one get a labelled placeholder.

## 8.4 Editing interactions and undo/redo

- All state changes pass through commands; there is no direct mutation. Commands produce forward and inverse JSON patches, which also serve as the basis for a future collaboration/CRDT adaptation.
- Gestures (drag, resize, rotate, typing bursts) are coalesced into a single history entry using a coalescing key and a time window. Pointer gestures additionally hold their key open (`DeckStore.beginGesture`) so a pause does not end them; keyboard bursts (a held arrow key) rely on the window alone. Operations that touch several elements in different ways (duplicate, paste, rotating a selection) are one `Batch` command.
- Selection and viewport (zoom, scroll) are UI state, not part of history.
- Patches are a subset of RFC 6902 (`add`, `replace`, `remove`, JSON-pointer paths) applied immutably, so undo keeps the identity of untouched slides and elements. `applyPatch` refuses `__proto__`, `constructor` and `prototype` keys and out-of-range paths (`PatchError`); `diff` therefore replaces an object that has such a key as a whole instead of descending into it, and treats inherited names such as `toString` as absent.
- The coalescing window slides: each merged command extends it by 500 ms. Gestures should supply a key per gesture (e.g. `drag:<ids>`); `SetNotes` coalesces per slide by default.
- Command-level rules (DT-02): a deck always keeps at least one slide (`DeleteSlide` of the last one throws); `SetProps` accepts only the shared element fields and the fields of that element type in `ELEMENT_SCHEMAS`, never `id` or `type`; `SetProps` checks scalar values against the field kind (finite numbers within the schema bounds, strings, booleans, enum members, non-negative integer `step`) and rejects removing required fields, while structured values (colours, fills, tables, code props) are left to the editor and `validateDeck` on load (tables have their own commands that keep the grid, widths and fills in step, `table-commands.ts`); `ResizeElements`, `MoveElements` and `SetProps` all reject non-finite numbers and unknown ids, even for a zero move; locked elements are not enforced by commands, that is the editor's concern; `DuplicateSlide` creates fresh ids for the slide and its elements; `AddSlide` rejects element ids that already exist in the deck (element ids are resolved deck-wide); `AddCodeElement` adds the `ComponentDef` only if its id is not in the deck yet, reuses an identical existing definition, and rejects a different one under the same id (edit shared definitions with `SetComponentSource`). `SetSlideSection` trims the name, treats a blank one as removal and caps it at 200 characters (it coalesces per slide like `SetNotes`); `SetSlideLayout` requires an existing layout and re-flows placeholder content (8.7), never adding or removing an element; the layout commands of DT-31 (8.7) validate as described there; `SetProps` accepts `sizeToken` only as a non-empty key of the deck's `typeScale` and removes it when `fontSize` is set without it; `SetTheme` validates the theme with `validateTheme` (same rules as on load) and refuses one that lacks the `background` / `text` colours or the `body` font the renderer falls back on, a colour token or font key that slides, layouts or elements still use, or a font face whose asset is missing or not a `font/*` asset, a family embedded twice, or an embedded family that no font stack names, and stores a copy of its argument; `SetSlideBackground` requires an existing asset for an image fill and removes the field for `undefined`; `AddAsset` accepts only an id that is the lower-case hex SHA-256 digest and equals both `hash` and `blobKey` of the reference (so `__proto__` and similar ids never become keys), is a no-op for an identical reference and rejects a different one under the same id; `DuplicateSlide` does not copy the section start. Component commands (DT-13): `SetComponentSource` and `AddCodeElement` (for a definition that is new to the deck) run `validateComponent`, so a source past 1,000,000 characters is refused instead of producing a deck that fails to load; `SetComponentDef` accepts a name of 1 to 200 characters, a prop schema, permissions, `files` and `libs` that pass `validateComponent` (duplicate or hostile keys, defaults outside their range, unknown permissions and assets that are not in the deck are errors), deduplicates the lists and is a no-op for equal settings; `SetCodeProps` accepts only keys of the component's `propSchema` (not inherited names), checks every value with `propValueProblem`, requires an `asset` prop to name an asset of the deck, and throws without changing anything if one is wrong; `DetachComponent` copies the definition under a fresh id made at construction (so redo replays the same id), renames it "<name> (copy)", moves only that element and refuses an element that is the only user. If the current slide is removed, the store selects the slide now at the same position (or the last one).
- Text editing inside an element uses ProseMirror's own history while focused; on blur (or Escape, or when the selection moves away) its changes are committed as one `SetText` command, and only if the content differs from what the edit started from, so opening and leaving a text leaves no history entry. The editor refuses any change that would take the document past the stored format's limits (nodes, characters, list depth), so what is typed can always be saved. If a commit is refused all the same (the element was deleted meanwhile, a theme token it names has gone) the failure is announced and the editor stays open once, so nothing typed is lost; leaving again discards the text.

## 8.5 Persistence

- `DeckRepository` (abstract class, 5.6): `list()`, `load(id)`, `save(deck, expectedRevision)`, `delete(id)`, `putAsset(blob)`, `getAsset(id)`, `listComponents()` / `putComponent(entry)` / `deleteComponent(id)` (the component library; `putComponent` refuses an entry that does not pass `validateComponent` or lacks the ref of an asset it names). Implementation: IndexedDB (`idb`) with stores `decks`, `assets`, `components` (the component library, 5.6), `meta` and `backups`; an in-memory implementation serves tests. Both are checked by one contract suite. Methods return `Result<T, PersistenceError>` and never reject.
- **Autosave** is debounced (500 ms, at most 5 s under a continuous gesture) and writes the deck JSON only, as one transaction over `decks` and `meta`. Whole-deck writes are accepted for now: cost follows deck size, not the size of the change. `save` does not run `validateDeck` (it would add a second full pass and could turn a bug into lost work); `load` validates, so an invalid stored deck is reported as `invalid-deck`.
- **Assets** are content-addressed: the id is the lower-case hex SHA-256 of the bytes, which is also `AssetRef.blobKey` and `AssetRef.hash`. Identical content is stored once (`created: false` on a repeat; the first mime type wins so refs and blob agree), saving a deck never touches the `assets` store, and bytes are stored as `ArrayBuffer` rather than `Blob`. `putAsset` applies the mime allow-list of 8.1 (exact match, no parameters). Assets are shared between decks, so `delete(deckId)` leaves them; garbage collection of unreferenced blobs is not built.
- **Concurrent tabs:** every deck has a `revision` (in the small `summary:<id>` record in `meta`, so the check reads no deck body), incremented on each save. `save` takes the revision the deck was loaded with (`null` for a new deck) and fails with `conflict` if the stored state differs, inside the same transaction. This also covers two tabs that both migrate an old deck: the first save wins, the second gets a `conflict`, and the backups of both loads exist. No Web Lock is used.
- **Read-only decks:** a stored deck whose `schemaVersion` is newer is never overwritten (`save` answers `read-only`), and `AutosaveService.open` returns the read-only outcome without touching the open deck.
- **Backups:** `IndexedDbDeckRepository` is the `BackupSink` of `migrateStored`. Each entry is `{ seq, deckId, fromVersion, toVersion, createdAt, raw }`. At most 5 are kept per deck: the oldest is never evicted, so a later migration cannot remove the only genuine pre-migration copy; beyond that the newest win. `delete(deckId)` removes the deck's backups. A migrated deck is stored only on the next save; loading an old deck again adds another backup, which retention bounds.
- **Failure:** an exception inside a transaction aborts it, so a partly queued save commits nothing. `QuotaExceededError` becomes `quota`, anything else `storage`; `AutosaveService` shows these through `PersistenceBanner` (6.5).
- **Eviction and reminders:** the app initializer calls `navigator.storage.persist()` (`AutosaveService.requestPersistence`). Each save records `unexported:<id>` with the time of the first save since the last export; `listUnexported()` / `markExported(id, revision?)` are the data for the export reminder (7.4), the UI for the reminder is not built yet; "Export" and "Export all decks" call `markExported(id, revision)` after the file was written.
- `.deck` format (ADR-007, built in DT-16, `library/archive/`): a ZIP (fflate) containing `deck.json` (the deck as compact JSON), `assets/<sha256>.<ext>` per asset (extension from the mime type: `png`, `jpg`, `gif`, `webp`, `avif`, `svg`, `mp4`, `webm`, `mp3`, `ogg`, `wav`, `woff`, `woff2`, `ttf`, `otf`, `js`, `css`, `json`), an optional `thumbnail.png` (the writer can include one, nothing produces one yet) and `manifest.json` (`format`, `formatVersion` 1, `appVersion`, `schemaVersion`, `contentHash` = SHA-256 of `deck.json`). `writeArchive` checks every asset against its id and size first, applies the reader's size limits (so it never writes a file the reader refuses for size; the compression ratio is not checked), stores pictures, video, audio and fonts uncompressed and text deflated, and stamps a fixed time on the entries, so the same deck always gives the same bytes. Reading is described in 8.2.
- **Export and import in the app:** `DeckArchive` exports a stored deck (read through the repository, so an older deck is migrated first), asking `FileAccess` to save it as `<title>.deck`; "export all" packs one `.deck` per deck into `decktech-decks.zip` (browsers ask before several downloads, and one file is one backup), skipping decks from a newer version and naming them. A bundle is for backup: import takes a single `.deck` and refuses a bundle (unpack it first). `FileAccess` uses `showSaveFilePicker` / `showOpenFilePicker` where they exist (feature-detected on each call) and otherwise a download through an anchor and an `<input type="file">`; a dismissed dialog is "cancelled", not an error, and a picker that refuses because the click that allowed it is gone (building a large archive takes time) falls back to the download. The failure banner's "Download .deck" exports the open deck as it is in memory. The whole file is held in memory, unzipped synchronously on the main thread (11.2).

## 8.6 Offline and dependencies

Code components can include libraries (e.g. D3, Three.js, Chart.js). To keep decks working offline and reproducible, libraries are **vendored into the deck** as assets and exposed through an import map. The editor offers "Add library" (from file, or fetch-and-vendor from npm via a CDN once while online). Direct CDN links are possible only with the `network` permission and are flagged as an offline risk in the editor. Built (DT-11): the host reads each library asset and sends its bytes in `init`; the runtime turns them into blob URLs and an import map keyed by the asset id, and always gives them a JavaScript MIME type. Built (DT-13): "Add library" in the code editor, from a file or from npm through `https://esm.sh/<package>@<version>?bundle` (a request the author starts, once, while online; the response must be JavaScript, at most 5 MiB and free of imports from the network, else it is refused), stored through `putAsset` and added to the definition's `libs` on "Done"; the editor flags code that loads from a network address as an offline risk. Naming a library (a friendlier specifier than its hash) is a later issue.

## 8.7 Theming

Theme tokens (colors, font families, type scale, spacing) are defined once per deck and referenced by built-in elements by token name. They are injected into code components as CSS variables, so a restyled deck restyles its components too. Layouts define placeholder positions.

- **Themes.** Elements store colour tokens (`{ token }`) and font keys, never the resolved value, so `SetTheme` restyles every built-in element by replacing `Deck.theme` alone; the renderer turns the tokens into `--deck-*` custom properties on the stage (shared with code components, 8.3). Two themes ship, `light` and `dark` (`BUILT_IN_THEMES`), with the same token names (`background`, `text`, `muted`, `accent`; fonts `heading`, `body`, `mono`) so switching never leaves a dangling reference; their text, muted and accent colours reach 4.5:1 on the background, which `themes.spec.ts` checks with `contrastRatio`. The theme picker swaps colours, type scale and spacing and keeps the deck's own fonts and font files; colour tokens the built-in theme lacks are kept. A theme counts as built-in when it has all of that theme's colours and exactly its type scale and spacing, else the picker shows "Custom"; if a change is refused the select goes back to what the deck has. Rich text size marks name `typeScale` keys, so `SetTheme` refuses a theme that lacks one that is in use (the built-in themes share their keys, so the picker never hits this). A text element takes its size from the type scale when it has `TextEl.sizeToken` (a key of `Theme.typeScale`): `effectiveFontSize(el, theme)` gives the token's size, else `fontSize`, which stays as the fallback (also if the token has gone), so changing the scale resizes that text with no per-element edit. New slides (`createPlaceholderElement`) and inserted titles, bullet lists and text boxes get `sizeToken` `heading`, `body` or `caption` when the theme has the key; "Size" in the properties panel switches an element between a theme size and "Custom size" (typing a font size in `SetProps` drops the token, else the number would be ignored). `SetTheme` refuses a theme that lacks a size token in use, like colours. `sizeToken` was added as an optional field without a `schemaVersion` bump (like `Slide.section`), and so was `Theme.name`.
- **Theme editor.** `ThemeEditor` (`editor/theme-editor.ts`, a modal opened by "Edit theme…") edits a draft of the deck's theme: name, colours, font stacks, type scale and spacing, with add and remove of tokens (the required `background` / `text` colours and `body` font, and tokens the deck still uses, cannot be removed there). Values are checked as typed (colour literals as the validator does, font stacks as the renderer does, sizes as numbers from 0). "Apply theme" is one `SetTheme` (one undo step; a refusal by the deck is shown in the dialog). The contrast of `text`, `muted` and `accent` against `background` (`themeContrast`) is shown live and a ratio below 4.5:1 is a warning (it does not block applying); colours that are not hex literals are reported as not measured. Embedded font files are not edited there. A theme with a `name` shows it in the toolbar picker instead of "Custom". A named theme is kept in the deck only: a library of themes shared between decks is not built (11.2).
- **Layout editor.** `LayoutEditor` (`editor/layout-editor.ts`, "Layouts…") edits the deck's layouts straight in the store, each change one command and so one undo step: `AddLayout`, `DuplicateLayout` ("<name> copy"), `RenameLayout`, `DeleteLayout`, `SetLayoutBackground`, `AddPlaceholder`, `SetPlaceholderBox` (move and resize, the rectangle in full), `SetPlaceholderKind` and `RemovePlaceholder` (`core/store/layout-commands.ts`). Rules: layout ids are valid ids and unique, a name is 1 to 100 characters, placeholder ids are unique within the layout, a placeholder lies inside the deck's stage with a width and height above 0 (checked even for a no-op), a background passes the fill validation (tokens and images must exist), at most 100 layouts and 50 placeholders. A deck keeps at least one layout. `DeleteLayout` of a layout that slides use is refused unless a replacement layout is given; with one, those slides move to it and their placeholder content re-flows in the same step, so no slide is ever left with a `layoutId` that does not resolve (the dialog asks which layout to use). Every layout edit re-flows the slides that use that layout with `reflowToLayout` (a moved placeholder takes its bound elements along; a removed one leaves them where they are, still bound). The preview shows the stage scaled to 640 px; a placeholder moves with the pointer, with the arrow keys (1 unit, Shift 10), resizes with the corner handle or Ctrl+arrows, and has number fields for X, Y, Width and Height, so no pointer is needed; keys clamp to the stage, and a pointer drag is one history entry through `beginGesture`.
- **Placeholders on the canvas.** The editor canvas draws dashed outlines (labelled with the kind, `aria-hidden`, no pointer events) for the current slide's layout; the presentation, presenter view and thumbnails never do, since the outlines belong to the editor's overlay, not to `SlideRenderer`.
- **Image placeholders.** `InsertActions.insertImage` puts a picture into the next free image placeholder of the slide's layout (`freePlaceholder`: the n-th placeholder of the kind, n being the number of elements already bound to the kind) with `placeholder: 'image'` and the placeholder's box, `fit: contain`, so it re-flows with the layout; with none free it is centred and unbound as before.
- **Layouts and placeholders.** A built-in layout has fixed ids (`ly_blank`, `ly_title`, `ly_title-content`, `ly_two-column`, `ly_title-only`) and placeholder ids unique within it; every deck stores its own copies. An element is *bound* to a placeholder kind by `Element.placeholder` (`title`, `body`, `image`, `footer`). A new slide made from a layout (`instantiateLayout`) gets a bound text element for each title, body and footer placeholder, styled from the theme (heading font and size for titles, body size, caption size for footers); image placeholders create no element because a picture needs a file. `SetSlideLayout` re-flows with `reflowToLayout`: per kind, the n-th bound element in z-order takes the n-th placeholder of that kind in the new layout (position, size, rotation reset to 0). Unbound elements, locked ones (which still use up their slot, so nothing is moved onto them) and bound ones with no placeholder left keep their geometry and binding, so no content is lost and switching back picks them up again; the command is reversible by undo like any other. The layout's `background` shows through where the slide has none.
- **Embedded fonts.** `Theme.fontFaces` lists `{ family, assetId }` pairs; the asset is a `font/woff2|woff|ttf|otf` blob in `Deck.assets` (content-addressed like pictures, 8.5). The renderer's `FontFaces` service registers them with `FontFace` (blob URL) so the deck does not depend on installed fonts (risk R7); faces the current theme no longer lists are removed again, so a stale file never wins a family name. Family names match `^[A-Za-z0-9][A-Za-z0-9 _-]{0,63}$`, so they are safe inside a CSS font stack, and "Add font…" derives the family from the file name (a name equal to an existing theme font such as `body` is refused), stores the file, and in one undo step adds the asset, the face and a `Theme.fonts` entry (`"Family", sans-serif`) that the Font field of a text element then offers.

## 8.8 Accessibility

- The editor UI is keyboard-operable: every canvas action (select next element, nudge, resize, reorder) and every sorter action (select, add, move, duplicate, delete) has a shortcut, declared through `ShortcutRegistry`, which refuses conflicting combinations and feeds the `?` help; focus order and visible focus rings are maintained; panels use proper roles and labels; colors meet AA contrast. Dragging (slides in the sorter) has a single-pointer alternative (Move up / Move down buttons, WCAG 2.5.7). Modal dialogs (insert menu, shortcut help) trap focus, close on Escape and return focus to what opened them.
- The in-place text editor is a labelled `role="textbox"` (`aria-multiline`) that is focused when an edit starts, announces "Editing text. Press Escape to finish." and "Text updated", and hands focus back to the canvas on Escape; its format controls are native buttons (`aria-pressed`) and selects with labels, reachable by Tab without ending the edit, and Tab inside the text is not captured (indent is Ctrl+]), so it is no keyboard trap. Rich text renders as `h1`-`h3`, `p`, `ul` / `ol` / `li`, `strong`, `em`, `u`, `code` and `a`.
- Slides render as semantic HTML (headings, lists, `alt` text for images); elements that are hidden or not yet reached by the step are not in the DOM when presenting, and thumbnails are `aria-hidden` and `inert` (5.7). The "reading order" panel (5.4) lets authors fix tab order: a slide's element array is z-order, DOM order and reading order at once, so moving an element earlier also sends it further back; there is no separate reading order yet.
- Presentation mode honours `prefers-reduced-motion` (transitions off) and exposes an ARIA live region announcing slide changes ("Slide 2 of 5, step 1 of 3"); the live region is the view's own, not the shell's, so it is inside the fullscreen element. Slides that are only preloaded are `inert` and `aria-hidden`. Its AXE test runs in unit tests (5.5).
- Code components receive `prefers-reduced-motion` and contrast information through the runtime; the app cannot guarantee their content is accessible and shows a checklist in the code editor (five items plus automatic hints, 5.3). The code editor is a modal dialog (focus trap, Escape, focus returned), a tab list with arrow-key navigation, and its questions (permission consent, discard) take the focus; its AXE test runs in unit tests (the preview frame is excluded: jsdom cannot inspect it).
- App-wide pieces live in `shared/` (5.8): a skip link as the first focusable element, a `main` landmark, one polite live region (`LiveAnnouncer`) for status messages, and a `FocusTrap` for dialogs. Controls that are briefly unavailable use `aria-disabled` instead of `disabled`, and built-in templates set text colours that reach AA on their backgrounds. Interactive controls are native elements; actions on repeated rows carry the row's title in their accessible name.
- The colours of the app chrome, their contrast, the focus ring, `forced-colors` and `prefers-reduced-motion` are defined by the design tokens and checked by `npm run lint:tokens` (8.11).
- Automated AXE checks run in CI against the library today and against the editor and presentation views as they are built (jsdom has no layout, so colour contrast is not checked by AXE there; the built-in themes' text, muted and accent colours are checked against their background with `contrastRatio` in unit tests instead; other colours are chosen by hand).

## 8.9 Error handling and logging

- `ErrorService` (`core/errors`) collects errors of the host and of code components, tagged by component id (`source` is `host` for the supervisor's reasons for ending a frame, `component` for what the component raised), newest 200, messages cut at 2000 characters. Nothing leaves the browser: there is no remote telemetry. Autosave failures keep their own banner (6.5) and are not routed through it yet.
- `HostConsole` (`components/host`) collects what components log and the errors they raise, plus the supervisor's reasons, tagged by component id, newest 200 only. The console panel of the code editor (5.3) reads it.
- Failures never lose data: `AutosaveService.flush()` runs before risky operations (opening another deck; import does not need it, since it never replaces the open deck) and migrations keep the previous version in a rolling backup store (`BackupSink`, see 8.1 and 8.5). A failed write keeps the changes pending and visible in the banner (6.5).

## 8.11 Visual design

The app chrome (library, editor, dialogs, presenter controls) gets one look from **design tokens and a few shared primitives, with no UI library** (ADR-012). Built (DT-44): the tokens, the base layer, the colour scheme switch and the checks, the shared primitives and the icon set, the editor toolbar redesign, and every screen restyled with them (library, editor shell, sorter, canvas toolbar and surround, properties panel, notes, insert menu, shortcut help, theme and layout editors, code editor and component library dialogs, trust dialog and code inspector, persistence banner, presentation and presenter view). The default scheme is `system`.

- **Tokens** are CSS custom properties on `:root` in `src/styles.css`, the only place (besides deck and slide code) where colour literals may appear: surfaces (`--surface`, `--surface-raised`, `--surface-sunken`, hover and active), lines (`--border` for decoration, `--border-control` for the edge of a control, which reaches 3:1), text (`--text`, `--text-muted`, `--text-disabled`), the accent (`--accent` as a fill with `--accent-text` on it, `--accent-ink` as text or icon on a surface), status colours (`--danger*`, `--warning-ink`, `--success-ink` with `*-subtle` backgrounds), `--focus`, the type scale (`--font-size-xs` to `-2xl`), a 4 px spacing scale (`--space-1` to `-7`), control heights (compact by default, never below 24 px, WCAG 2.5.8), radii, shadows, motion durations and layers. A comfortable density is optional and not built.
- **Light and dark.** The light set is the default on `:root`. The dark set is written twice: inside `@media (prefers-color-scheme: dark)` for `:root:not([data-theme='light'])` and under `:root[data-theme='dark']`. Plain CSS cannot share the block between the two, so `scripts/check-tokens.mjs` fails if the copies differ. `ColorScheme` (`shared/color-scheme.ts`) holds the mode `light`, `dark` or `system`, stores it in `localStorage` under `decktech.colorScheme` (a blocked store only costs persistence) and sets `data-theme` on `<html>`; `system` removes the attribute. A small inline script in `index.html` sets the attribute before the first paint, so there is no flash of the wrong mode. `ColorSchemeSwitch` is the labelled select for it. The first-visit default is `system` (`DEFAULT_COLOR_SCHEME`, repeated in the `index.html` script: change both together; a legacy value is ignored).
- **Deck themes stay separate.** `Theme` (8.7) styles the slide stage through `--deck-*` properties set on the stage element; chrome tokens have other names and are never read by the renderer, and the renderer never writes to `:root`. A dark chrome therefore does not change how a slide looks, and a dark deck theme does not change the chrome.
- **Accessibility.** Every text pair, the focus ring and the control edge reach AA (4.5:1 text, 3:1 focus and control edges) in both modes, on every surface; `findCssProblems` checks that list (`PAIRS`) in `scripts/check-tokens.test.mjs`, which `npm run test:scripts` runs. `:focus-visible` draws a 2 px `--focus` outline. Under `forced-colors: active` (the selector is `:root:root:root` so it outranks the dark sets) `--focus` is `Highlight` and the control and decorative borders use system colours. Under `prefers-reduced-motion: reduce` the three duration tokens are `0ms`, so any transition written with them stops.
- **The checks** (`npm run lint:tokens`): a colour literal (`#rgb[a]`, `#rrggbb[aa]`, `rgb()`, `hsl()`, `hwb()`, `lab()`, `lch()`, `oklab()`, `oklch()`) in chrome code fails unless the file is on the baseline `scripts/token-baseline.json` with at least that many. The baseline is empty now (all legacy literals are gone), so any new literal fails; `--update` rewrites it. A line containing `token-check-ignore` is skipped, for a colour that is data (the default of a deck colour, a hint such as "#112233"); `app/core/persistence/persistence-banner.ts` is chrome in an exempt folder and is checked. Not checked: colour keywords such as `white`, and the exempt code, which is `core/`, `renderer/`, `components/host/`, the built-in code components, the stress deck, the templates and specs. The baseline is the list of screens still to migrate (11.2).
- **Primitives** (`src/ui.css` for the look, `app/shared/` for the behaviour; ADR-012). Classes over the tokens, usable from any component because the stylesheet is global: `.btn` with `.btn-primary`, `.btn-quiet`, `.btn-danger`, sizes `.btn-sm` / `.btn-lg`, `.btn-icon` (a square the height of the control, never below 24 px), `.btn-group` and `.toolbar-separator`; a toggle is a `.btn` with `aria-pressed` (or `aria-expanded`), a briefly unavailable one has `aria-disabled="true"` (same look as `disabled`, stays focusable). Every state (hover, active, pressed, disabled) is defined once. Controls: `.field` / `.field-label` / `.field-hint` / `.field-error`, `.input` (text, number, select, textarea; `aria-invalid` and `aria-disabled` styled), `.check` over the native checkbox. Also `.tablist` / `.tab`, `.badge` (plain, accent, danger, warning, success), `.kbd`, `.notice` and the dialog classes. Components: `Icon` (`app-icon`), `Tooltip` (`appTooltip`), `Dialog` (`app-dialog`), `Tabs` (`app-tabs`) and `Notice` (`app-notice`).
- **Icons.** `ICONS` (`shared/icons.ts`) maps about fifty names to the `d` of one path on a 24 px grid, drawn as a 2 px round stroke in `currentColor`; `app-icon` renders it as an `aria-hidden` inline SVG sized by the surrounding font size. No icon font and no network. The control around an icon must have a name: visible text, `aria-label`, or `appTooltip`.
- **Tooltip.** Shows after 400 ms of hover and at once on keyboard focus (not on focus a mouse press caused), stays while the pointer is on it, and Escape dismisses it without closing a dialog around it (WCAG 1.4.13). The text is appended to `<body>` as a `role="tooltip"` element placed below the control (above if there is no room) and kept inside the viewport. `appTooltipShortcut="Ctrl+B"` adds a `kbd` and `aria-keyshortcuts` (`Control+B`). A control with neither text nor `aria-label` gets the tooltip text as its name, so an icon-only button cannot be unnamed by forgetting it. Tooltips do not open on touch.
- **Dialog and tabs.** `app-dialog` is the shell of a modal: backdrop, header with the title (`aria-labelledby`) and a close button, scrolling body, footer slot `[dialog-footer]`, `FocusTrap` for focus in and back, and `closed` for Escape, the backdrop and the close button; the consumer removes it. Escape is stopped there, so a dialog above another closes alone. `app-tabs` is the strip only (WAI-ARIA tabs, automatic activation, one tab stop, Left / Right / Home / End with wrap); the consumer renders the panel and uses `tabId` / `panelId` for the `aria-controls` / `aria-labelledby` links. `app-notice` says its kind with an icon and a hidden prefix ("Warning: "), never by colour alone, and uses `role="alert"` for warnings and errors and `role="status"` otherwise.
- **Checks on the primitives.** `lint:tokens` also fails when `ui.css` or `shared/` use a `var(--x)` that `styles.css` does not define (`--deck-*` is the slide stage's), and `check-tokens.test.mjs` holds `ui.css` to: no colour literals, every button variant and state present, icon buttons sized by the control-height tokens, no removed focus ring, a `forced-colors` block. Behaviour and AXE are tested in `shared/primitives.spec.ts` (jsdom has no styles or layout, so contrast is the token check's job). The existing dialogs and toolbars still use their own CSS and move to these in the screen slices.
- **Presentation colours.** Presentation mode is black whatever the scheme, so it has its own tokens (`--present-bg`, `--present-text`, `--present-overlay`) that dark mode does not override; the floating controls are the shared button in those colours. The presenter view follows the chrome scheme. `--guide` is the colour of snapping guides on the canvas.
- **Editor toolbar.** Insert / Add slide, the two selects with icon buttons for the theme and layout editors, Present as the primary action, and the overflow menu, in one `nowrap` row; the canvas toolbar is made of small quiet buttons. Dialogs keep their own shells (`editor/dialog.css`, `components/editor/tools-dialog.css`, the library's delete dialog uses the `.dialog-*` classes); those files now hold only layout and the dialog frame, built from tokens, while buttons, inputs, tabs and notices come from `ui.css`. Moving them onto `app-dialog` is left (11.2).
- **Base layer, deliberately narrow.** The base layer sets the page colours, font family, focus ring, selection and scrollbar colours, and no global `box-sizing` or font size, so a screen that has not moved to the tokens does not shift.
